# Declared breaking changes for docs/catalog/public-openapi.yaml.
#
# oasdiff --err-ignore matches by SUBSTRING: an entry suppresses a breaking
# change when the entry line CONTAINS oasdiff's own error text verbatim
# ("in API <METHOD> <path> <description>"), so prose may surround an entry but
# never interrupt it. Lines that match nothing — this header included — are
# inert. Removing an entry re-arms the gate for that change.
#
# Wave 190 (2026-08-08) corrects the error envelope on all 25 operations:
# application/problem+json + RFC7807 ErrorModel became application/json +
# HouseError {code,message,data}.
#
# READ THE DIRECTION CAREFULLY — this is not the service changing. The service
# has ALWAYS answered errors with the house envelope: huma.NewError is a
# package-level var, and every runtime mount of catalog swaps it (handler/
# admin.go, s2s.go, user_cover_votes.go) before registering anything. The one
# caller that skipped the swap was the spec-only path, SetupCatalogPublicSpec,
# which therefore froze Huma's stock RFC7807 model into the PUBLISHED contract.
# So for the whole life of this spec the document has been describing an error
# body no deployment ever sent, and any client generated from it had its error
# handling written against a fiction. Proven by diffing the frozen YAML against
# the spec the production binary serves at /v1/catalog/openapi.json: the error
# envelope was the ONLY disagreement between them, and it is now gone.
#
# oasdiff is right to call it breaking — a consumer that matched on
# application/problem+json will stop matching. But that consumer was already
# broken at runtime; what changes here is only that the document stops lying
# about it. No deploy accompanies this: the served spec is already correct.
# Rationale and the corrected contract text: docs/developer-platform/02-public-api.md §3.6.

# Wave 194 (2026-08-08) removes the name{ja,zh,other} buckets from PublicName,
# PublicCharacter and PublicSiblingName — and therefore from names/{id},
# characters/{id}, lookup and lookup/batch, which embed those records.
#
# The shape was a false trilingual. It never held three names: the registry
# files the ONE name of record into whichever bucket its own language falls in,
# so at most one was ever populated. What that could not express is the case
# that mattered — a Japanese name WITH a Chinese rendering on file published
# {"ja": "…"} and no zh key, which every consumer reads as "no Chinese name
# exists" while the rendering sat unreachable in catalog_name_alias.
#
# The replacement shipped first and is live: display_name + lang (the name of
# record and its own BCP-47 tag) plus localized{} (per-locale renderings, keyed
# canonically), waves 191/192/193. Contract rule:
# localized[locale] ?? display_name ?? latin.
#
# Every consumer was measured, not assumed. forum was the only repo decoding
# these buckets; it adopted in 79fd3cc0 and is deployed — verified in production
# on 2026-08-08, where GET /api/galgame-staff/74 now answers name_zh "伊东杂音",
# a value the buckets could never publish. patch decodes no buckets at all: its
# lookup DTO reads only work + claimed_by. letmoe is not launched and is out of
# scope. Rationale and the migration note: docs/developer-platform/02-public-api.md §3.7.
